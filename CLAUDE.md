# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

KMCC Savings & Loan Management — a PWA for tracking member savings, loans, profit/interest distribution, and expenses (including zakat). Monorepo with three parts sharing one Postgres (Neon) database.

## Commands

Run from repo root unless noted.

- `npm install && npm --prefix server install && npm --prefix web install` — install all three package.json's (root, server, web are separate npm packages, not an npm workspace)
- `npm run dev` — runs the API (port 4000, from `server/`) and web (port 5173, proxies `/api` to the API) concurrently
- `npm run dev:api` / `npm run dev:web` — run just one side
- `npm run prisma:migrate -- --name <name>` — create/apply a migration against `DATABASE_URL` (delegates to `server/`, schema lives at `prisma/schema.prisma`)
- `npm run prisma:generate` — regenerate the Prisma client into `server/node_modules/.prisma/client`
- `npm run seed` — seeds one admin login (`mobile: 9999999999`, `memberCode: KMCC0001`, `password: admin123`) and one default Bank row
- `npm run seed:members` — bulk-seeds member records (mobile `123456`, password `123456`) from the name list in `server/src/seedMembers.ts`
- `npm --prefix server run build` — `tsc` build of the API (used for typechecking; `npx tsc --noEmit` in `server/` also works)
- `npm --prefix web run build` — `tsc -b && vite build`; also generates the PWA service worker/manifest

There are no automated tests yet.

### Environment

Copy `.env.example` to `.env` at repo root AND to `server/.env` (the API loads its own `.env` via `dotenv/config`, it does not read the root one). Needs `DATABASE_URL`, `DIRECT_URL` (Neon pooled + direct connection strings), `JWT_SECRET`, `PORT`. The web app has no required env var in dev — it hits `/api` via the Vite proxy (`web/vite.config.ts`) and falls back to `/api` in production via the Vercel rewrite in `vercel.json`.

### Before pushing

Run this checklist before every `git push` (not just when asked — do it automatically as part of finishing any change):
1. `npx tsc --noEmit` in `server/` and `npx tsc -b --noEmit` in `web/` — both must be clean.
2. `npm run build` in `web/` — production build must succeed.
3. If any `.tsx` files changed, run the `vercel:react-best-practices` skill against them (component structure, hooks, accessibility, re-renders, TS patterns) and fix anything it flags before committing.
4. Only then `git add` the reviewed files, commit, and push.

`git push` itself is blocked by this environment's auto-mode safety classifier for Claude — after committing, tell the user to run `! git push -u origin main` themselves.

## Architecture

**Three packages, not an npm workspace** — `server/`, `web/`, and root each have their own `package.json` and `node_modules`. `prisma/schema.prisma` lives at the repo root but its generated client is output into `server/node_modules/.prisma/client` (see the `generator client { output = ... }` line) — that's why `server/src/lib/prisma.ts` and every route import from `.prisma/client`, not `@prisma/client`.

**API source lives in `server/`, but the deployed function is `api/index.ts`.** `server/src/app.ts` builds the Express app and mounts every router under an `/api/*` prefix internally. `server/src/server.ts` is the local dev entry (`app.listen`). The top-level `api/index.ts` is the *only* file inside `/api` — it imports the Express app from `../server/src/app` and is Vercel's serverless entry (`vercel.json` routes all `/api/(.*)` traffic to it). This split exists because Vercel's zero-config detector turns every file placed directly under `/api` into its own serverless function — Hobby plan caps that at 12, so the actual route/lib/middleware files must live outside `/api` in `server/`. When adding a new route file, put it in `server/src/routes/` and mount it in `server/src/app.ts` — never add files directly under `/api`.

**Auth model**: login is a single `username` field (mobile number OR `memberCode`) + password — not two separate fields. `server/src/routes/auth.ts` tries an exact `memberCode` match first (case/whitespace-normalized), then falls back to `mobile`; if multiple members share a mobile number (common right after bulk-seeding placeholder numbers) it returns an error asking for the Member ID instead of guessing. `memberCode` is an auto-incrementing `KMCC0001`-style code (`server/src/lib/memberCode.ts`). JWT payload is `{ memberId, memberCode, role }`; `requireAuth`/`requireAdmin` middleware (`server/src/middleware/auth.ts`) attach `req.user`. There is one `Member` model for both admin and regular users — `role: ADMIN | MEMBER` gates access, and `isSavingMember` / `isLoanMember` booleans (mutually exclusive, enforced in the API) drive what a member's profile page shows.

**Monthly savings contributions are auto-generated, not manually entered per month.** `server/src/lib/contributions.ts` has three key functions:
- `ensureContributionsUpTo(memberId, year, month)` — lazily backfills `MonthlyContribution` rows from a saving member's join month through the target month, using whatever `MonthlyAmountHistory` amount is set for each year. Called on-demand (e.g. when viewing a profile or recording a deposit), not via a cron.
- `allocateDepositToContributions(memberId, amount, date)` — applies a single deposit transaction across the member's oldest pending/partial months **within that deposit's own calendar year only** (a 2025-dated deposit can never fill 2026's months, and vice versa — each year is a separate obligation), so one lump payment can clear several back-months. Invoked automatically from `POST /api/transactions` whenever a `SAVING_DEPOSIT` transaction is created with a `memberId`.
- `recalculateAllContributions(memberId)` — resets a member's entire paid/pending history and replays their remaining `SAVING_DEPOSIT` transactions in date order. Called whenever a saving-deposit transaction is edited or deleted, so the schedule never has stale "paid" rows left over from a transaction that no longer exists.

Changing a member's monthly amount (`POST /members/:id/monthly-amount`) is keyed by `(memberId, year)` and also refreshes `amountDue` on that year's still-`PENDING` months (paid/partial months keep their historical amount — only untouched months follow the new rate).

**Profit distribution is a fan-out operation, not a single transaction.** `POST /api/transactions/profit-distribution` takes one lump sum + bank, computes each active saving member's share proportional to their cumulative `SAVING_DEPOSIT` total, and creates one `PROFIT` transaction per member, all tagged with the same generated `profitBatchId` so the batch can be deleted/audited as a unit (`DELETE /transactions/profit-distribution/:batchId`).

**`Transaction.bankId` is nullable, with one exception.** Every category except `SAVING_DEPOSIT` still requires a bank (enforced in `server/src/routes/transactions.ts`'s `POST /transactions`) — only a saving deposit can be entered without picking a bank, since admins often record member savings before reconciling which physical bank account received the cash. `memberId` is nullable for org-level entries (general expense, zakat) not attributable to one member; it's required for `SAVING_DEPOSIT`/`SAVING_WITHDRAWAL`/`LOAN_DISBURSEMENT`/`LOAN_REPAYMENT`. `Transaction.category` drives side effects in `server/src/routes/transactions.ts` via helpers in `server/src/lib/loans.ts`: `SAVING_DEPOSIT` triggers contribution allocation; `LOAN_REPAYMENT` adjusts `Loan.balance` and flips `Loan.status` to `CLOSED` when it hits zero.

**`SAVING_WITHDRAWAL` (category, `EXPENSE` flow) lets an admin withdraw a member's accumulated savings** — picked from the Withdrawal category dropdown on the Transactions page (bank required, like every non-`SAVING_DEPOSIT` category; member required, enforced in `POST /transactions` alongside the loan-linked categories). It has **no side effect on `MonthlyContribution`** — that schedule tracks monthly dues paid, a separate concept from the running savings balance being withdrawn from, so a withdrawal never un-pays a month. It reduces a member's Profile "Balance" for free (that Statistic is already a flow-based INCOME-minus-EXPENSE sum) and nets out of the dashboard's "Total Savings Amount" tile (`server/src/routes/dashboard.ts`: `totalDeposits - totalWithdrawals`) and its drill-down (`AdminDashboard.tsx` TILES entry filters `category=SAVING_DEPOSIT,SAVING_WITHDRAWAL`). It is **not** netted out of `profit-distribution`'s per-member share calculation, which still groups on gross `SAVING_DEPOSIT` only — a known follow-up, left alone since profit-distribution basis is one of the unconfirmed assumptions flagged below. Importable via CSV (`CATEGORY_ALIASES` in `transactions.ts` accepts `SAVING`/`SAVINGS`/`SAVING WITHDRAWAL`/`SAVINGS WITHDRAWAL`). `TransactionFormFields.tsx`'s `NO_PICKER_CATEGORIES` (renamed from `LOAN_LINKED_CATEGORIES`) excludes it from the Banks page's bank-only "Add Entry" form, which has no member picker to satisfy its member requirement.

**A member has at most one `ACTIVE` `Loan` row at a time** (`resolveDisbursementLoan` in `server/src/lib/loans.ts`, used by `POST /transactions`, `POST /transactions/import`). A `LOAN_DISBURSEMENT` tops up the member's existing `ACTIVE` loan (principal and balance both increase) if they have one; only if they have none (first loan, or a prior one is fully repaid/`CLOSED`) does it create a new `Loan` row. This means a repayment almost never needs to disambiguate which loan it's against — `LOAN_REPAYMENT` still requires `linkedLoanId` (enforced by both the `Select` in `TransactionFormFields.tsx` and `POST /transactions`, 400 if missing) but there's normally only one `ACTIVE` loan to pick. This matters because there is currently **no dedicated frontend UI** for the standalone `POST /loans` / `POST /loans/:id/repayment` endpoints (which still create a new `Loan` per call, unchanged) — every loan in the system, so far, has been created by picking category "Loan" on the generic Transactions/Banks "Add Transaction"/"Add Entry" forms, so `POST /transactions` has to replicate loan-creation behavior itself. Forgetting this is why the dashboard's "Total Loan Amount" (`sum(active Loan.balance)`, not a transaction sum) can silently read zero after adding loan-disbursement transactions — check this file's `POST /transactions` handler before changing loan-related transaction logic. **Editing or deleting a `LOAN_DISBURSEMENT`/`LOAN_REPAYMENT` transaction recalculates the linked `Loan` from its remaining transactions** (`recalculateLoan` in `server/src/lib/loans.ts`, called from `PUT`/`DELETE /transactions/:id`) — principal/balance/status are always derived by summing that loan's still-existing `LOAN_DISBURSEMENT`/`LOAN_REPAYMENT` rows, and the `Loan` row is deleted outright if none remain. Before this existed, deleting a loan transaction left the `Loan` row's balance untouched, silently drifting out of sync (this is also why repeatedly testing CSV import can leave orphaned zero-transaction `Loan` rows from before this fix — check for and delete any with no linked transactions if you see stale "multiple active loans" errors on old data). The frontend labels these flows "Deposit"/"Withdrawal" (`web/src/pages/Transactions.tsx`) even though the DB enum is still `INCOME`/`EXPENSE`. Because bank-less saving deposits don't show up in any bank's balance, `web/src/pages/Banks.tsx` has its own "Add Entry" button/modal — reusing the same `web/src/components/TransactionFormFields.tsx` flow/category/member/bank dropdowns as the Transactions page's Add Transaction form, but with `bankId` always required — so an admin can manually post the matching bank-side entry once they know which account it landed in.

`web/src/pages/Transactions.tsx` also has multi-select bulk delete: a `rowSelection` checkbox column plus a "Delete Selected (N)" toolbar button (only rendered when ≥1 row is checked) that fires one `DELETE /transactions/:id` per selected row via `Promise.all` — there's no dedicated bulk-delete API endpoint, it's just N calls to the existing single-delete route. Selection is cleared whenever the bank/category filter changes.

**Dashboard summary** (`GET /api/dashboard/summary`, `/api/dashboard/banks-summary`, `/api/dashboard/members-summary`, admin-only) is computed live via Prisma aggregates in `server/src/routes/dashboard.ts` — there's no materialized/cached summary table. The 7 amount tiles map directly to `Transaction.category` sums plus `Bank.openingBalance + sum(INCOME) - sum(EXPENSE)` for bank balance, and `sum(active Loan.balance)` for outstanding loans; an 8th "Total Members" tile shows active member counts (total/saving/loan) instead of a currency amount. `Bank.openingBalance` matters here — it's how a real-world existing account balance (entered from a bank statement) gets reflected from day one instead of starting at zero. "Total Bank Balance" and "Total Members" are the two drill-down tiles (colored top border + pie-chart badge to mark them as clickable, `web/src/pages/AdminDashboard.tsx`) — clicking either opens a donut-chart breakdown modal (conic-gradient built by hand, no chart library) whose list rows navigate to `/banks?bankId=` or `/members?type=saving|loan` respectively. `Banks.tsx` reads that `bankId` query param the same way `Transactions.tsx` does, to filter its own embedded transactions table (below the bank grid) down to that one bank; the "Filter by bank" `Select` on that page updates the same param.

**Frontend role-based routing**: `web/src/App.tsx` nests two `ProtectedRoute` layers — the outer requires any authenticated member, the inner (`allow={['ADMIN']}`) gates `/dashboard`, `/members`, `/banks`, `/transactions`. `/settings` and `/profile` are reachable by both roles. `/profile` (`web/src/pages/Profile.tsx`) is shared by both roles but behaves differently: a regular member always views their own data (name rendered as a bold page title, no picker); an admin gets a member-picker dropdown (defaults to the first member, name rendered smaller since the dropdown already shows the selection) and can view anyone's profile. The page conditionally renders a savings contribution schedule (with a 12-segment circular progress ring showing months paid out of 12) and/or a loan section based on the viewed member's `isSavingMember`/`isLoanMember` flags. **The top "Balance" `Statistic` is a net figure**: sum of `INCOME` transaction amounts minus `EXPENSE` transaction amounts across *all* of that member's transactions (not scoped to the current year, not gated by `isSavingMember`/`isLoanMember`) — this was changed from an earlier version that picked *either* lifetime `SAVING_DEPOSIT` total *or* `Loan.balance` depending on the member's type, which meant loan disbursement/repayment transactions posted against a savings-flagged member (or vice versa, via the generic Transactions form) never moved the number. The per-loan cards under "Loan Details" still show each individual `Loan.balance` separately. Auth state (`web/src/store/auth.ts`, zustand) persists the JWT and member object to `localStorage`; `web/src/api/client.ts` is the one axios instance everything should import — it auto-attaches the bearer token and logs out on a 401.

**Theme**: `web/src/store/theme.ts` (zustand) holds `light`/`dark`, defaulting to `dark` for anyone with no stored preference, persisted to `localStorage` under `kmcc_theme`, wired into antd's `ConfigProvider` `algorithm` in `App.tsx`. `/settings` (`web/src/pages/Settings.tsx`) exposes the toggle, plus self-service change-password (`POST /api/auth/change-password`) and contact-details editing (`PUT /api/members/:id/contact`, self or admin). **Any custom-styled element must read colors from `theme.useToken()`, never hardcode a hex/rgba** — this has caused real dark-mode bugs twice (the header background, the bank-breakdown donut's center hole) where a hardcoded `#fff`/light color made text invisible against the dark theme.

**Mobile responsiveness** is done per-page via antd's `Grid.useBreakpoint()` (`isMobile = !screens.sm`), not CSS media queries — see `Transactions.tsx`, `AdminDashboard.tsx`, `Banks.tsx`, `Profile.tsx` for the pattern (icon-only buttons, single-column `Descriptions`, smaller Statistic fonts, etc.). The mobile sidebar (`web/src/components/AppLayout.tsx`) switches to `position: fixed` with a click-to-close backdrop when open on mobile, so it overlays content instead of pushing it; antd's auto-generated zero-width-trigger hamburger is repositioned via `zeroWidthTriggerStyle={{ top: 12 }}` to sit inside the header band instead of colliding with page content or the member name.

**Transaction CSV import/export** (`Transactions.tsx` + `POST /api/transactions/import`) round-trips: export writes Date (`YYYY-MM-DD`)/MemberCode/MemberName/BankName/Flow/Category/Amount/Description/LoanId; import accepts the same columns back. Import's date parser (`parseImportDate` in `transactions.ts`) accepts both `YYYY-MM-DD` and `DD/MM/YYYY`/`DD-MM-YYYY`, since opening the exported CSV in Excel and re-saving commonly rewrites dates into the regional format. Bank is optional on import only for `SAVING_DEPOSIT` (mirrors `POST /transactions`). `LOAN_DISBURSEMENT`/`LOAN_REPAYMENT` rows **are** importable (previously rejected outright): a Loan-category row with `EXPENSE` flow disburses (tops up the member's existing `ACTIVE` loan, or creates one — see the one-active-loan-per-member note above); with `INCOME` flow it repays a loan, resolved via the row's `LoanId` column if present, else falling back to the member's single `ACTIVE` loan (errors out if the member has zero, or more than one — from pre-top-up-model legacy data — active loans and no `LoanId` given). **All `LOAN_DISBURSEMENT` rows in a batch are processed before any other row, regardless of their position in the sheet** (`processingOrder` in `POST /transactions/import`, a stable sort keyed on resolved category) — otherwise a repayment listed above its own batch's disbursement row would fail to find a loan to repay against, since the row processing itself is what brings the loan into existence. Results are tagged with their original row number so response ordering is unaffected by this reordering. CSV parsing/generation is hand-rolled in `web/src/utils/csv.ts` (no dependency). **A `0` amount is valid**, both on `POST /transactions` (`amount === undefined || amount === null || amount < 0` is the actual reject condition, not a truthy check — `0` used to be silently rejected) and on import (the amount cell must be present and parse to a non-negative number; a blank cell still errors, `0`/`"0"` doesn't). This lets an admin record a zero-value entry for the audit trail without it needing to carry a nonzero amount. `allocateDepositToContributions` (`contributions.ts`) already no-ops safely on a `0` `SAVING_DEPOSIT` (its loop breaks on `remaining.lte(0)` before writing anything, so no month gets falsely flipped to `PARTIAL`) — this was true before this change and needed no fix. A `0` `LOAN_DISBURSEMENT` for a member with no active loan **will** create a `Loan` row with principal/balance `0` and status `ACTIVE` (`resolveDisbursementLoan` in `loans.ts` has no zero-amount special case) — accepted as a deliberate consequence of allowing `0` broadly, not guarded against. **`POST /transactions/import` has a `dryRun: true` mode** that runs every validation/lookup (member, bank, date, loan resolution) without writing anything to the DB and returns a `preview: PreviewRow[]` array instead of `{ created, errors }` — each row comes back `status: 'ok'` (with a human-readable `loanNote` for loan rows), `'error'`, or `'needsLoanId'` (ambiguous repayment, includes `candidates: {id, balance, disbursedDate}[]` of that member's active loans). Because dry-run writes nothing to the DB, a `virtualLoans` map (memberId → simulated `{id, balance, label}`) tracks each member's resulting loan state across the simulated batch so a same-batch disbursement-then-repayment preview matches what the live run (which writes row-by-row and so sees its own earlier writes for free) will actually do. The frontend always calls dry-run first to render a preview table (`Transactions.tsx`'s `onImportFile`); rows that come back `needsLoanId` get an inline `Select` of candidate loans, and "Confirm Import" re-posts the same rows (without `dryRun`, merging in any picked `loanId`s) to actually commit — so an admin resolves loan ambiguity by picking from a list instead of needing to hand-edit a `LoanId` column into the CSV.

**PDF member statement** (`web/src/utils/pdf.ts`, triggered from the download icon on `/profile`): dynamically imports `jspdf` + `html2canvas` inside the click handler (kept out of the main bundle) and renders an offscreen HTML template — org header, avatar-photo-or-initials + member details + `KMCC.svg` logo, a running Credit/Debit/Balance ledger built from the member's transactions, and a static Malayalam footer — to a canvas that's sliced across paginated A4 pages. This is an **image-based PDF** (text isn't selectable, files run a few MB) because jsPDF's built-in fonts can't render Malayalam glyphs; switching to real embedded-font text is a known, deliberately-deferred follow-up. The org logo is referenced as an `<img src="/KMCC.svg">` rather than inlined SVG markup, since that file's masks/gradients/clip-paths aren't reliably rasterized by html2canvas when inlined directly. Each ledger row tracks `isCredit` (from `t.flow === 'INCOME'`) alongside its `credit`/`debit` numbers so a genuine `0`-amount transaction prints `0.00` on its own flow's column instead of collapsing to `-` — rendering used to branch on the numeric value being truthy, which meant a `0` credit/debit was indistinguishable from "this side doesn't apply to this row" (e.g. an expense row's credit column).

## Known open decisions

Several product behaviors were assumed rather than confirmed with the client and are flagged in the design plan (loan interest calculation stays fully manual, profit distribution is based on cumulative-not-yearly savings, every transaction requires a bank, member soft-delete). Before changing behavior in `contributions.ts` or `transactions.ts`'s profit-distribution logic, check whether the assumption has since been confirmed/changed.
